# psiphon-egress

Psiphon как второй выход для ноды xray / Remnawave. Он нужен для сайтов, которые
не пускают адреса дата-центров.

Туннель работает в контейнере. Его SOCKS5 публикуется на адресе, который доступен
только внутри хоста, и xray ходит в него через outbound из четырёх строк. Жизненным
циклом управляет systemd. Watchdog меняет выход, когда тот перестаёт быть
*пригодным*. Это другой вопрос, чем «жив ли туннель».

## Установка

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/mtvworks/psiphon-egress/main/psiphon_install.sh) \
  --no-http --bind-loopback --region 'DE,NL,FR,AT,CH,SE'
```

Нужны root, docker, curl, `ss` (iproute2) и `flock` (util-linux).

Все значения проверяются до того, как что-либо записывается: коды стран (в любом
регистре, через запятую или пробел), порты, IPv4-адрес в `--bind`, лимиты памяти и
процессов. Неверный ввод останавливает установку, а не попадает в файл, который
root потом исполняет.

Эти флаги стоят в примере не для красоты:

- `--bind-loopback` публикует SOCKS на `127.0.0.1`. Это правильно, если xray
  работает в сетевом пространстве **хоста**
  (`docker inspect --format '{{.HostConfig.NetworkMode}}' remnanode` выводит `host`).
  Если нет — уберите флаг, и установщик привяжет SOCKS к шлюзу docker0. До него
  достают контейнеры в bridge-сети.
- `--no-http` полностью отключает HTTP-прокси. В этой схеме он никому не нужен, а
  порт 8080 на нодах Remnawave часто уже занят: по умолчанию там слушает
  локальный API CrowdSec.
- `--region 'DE,NL,…'` задаёт пул стран для ротации. Без него установщик выбирает
  самый быстрый выход в любой точке мира — для европейской ноды это бывал Сингапур.

### Переустановка

Повторный запуск установщика сохраняет то, на чём остановился прошлый:
- порты;
- регион и пул, включая шаг, до которого дошли ротации;
- списки deny/accept и настройки watchdog;
- образ, уведомления и метрики.

Явно переданный флаг всегда важнее сохранённого значения. `--region ''`
возвращает режим auto.

## После установки — маршрутизация

Установщик печатает outbound. **Сам по себе outbound ничего не проводит**: конфиг
xray на ноде принадлежит панели, поэтому правила вносятся в панель, а не на ноду.

```bash
vps-psiphon routing
```

Обе UDP-строки из вывода обязательны. Этот SOCKS работает только по TCP: на UDP
ASSOCIATE psiphon отвечает `REP=7 COMMAND NOT SUPPORTED`.
- Если отправить UDP в туннель, вместе со всем остальным перестаёт работать DNS.
- Если оставить UDP напрямую, QUIC/HTTP3 продолжает успешно ходить *мимо*
  туннеля, и заметная часть трафика молча его игнорирует.

Блокировка UDP (с единственным исключением для DNS) переводит клиентов на TCP —
а этот путь работает.

## Проверка, что это не открытый прокси

```bash
vps-psiphon verify
```

Команда проверяет всех слушателей на порту SOCKS и на порту HTTP-прокси (он
открыт ровно так же). Она предупреждает и о wildcard-, *и* о публичных адресах,
проверяет, что SOCKS действительно работает, и печатает единственную внешнюю
проверку, которая что-то доказывает.

**Не используйте `nc -z` или любую другую проверку TCP-соединением, чтобы понять,
открыт ли порт наружу.** Некоторые провайдеры завершают TCP-рукопожатие на любом
порту, даже если на нём никто не слушает. На таком хосте `nc -z` показывает «open»
для надёжно закрытого порта — и точно так же для действительно открытого. Отличить
безопасный случай от опасного он не может. Это умеет только настоящее
SOCKS-рукопожатие:

```bash
# с другой машины — команда ДОЛЖНА завершиться ошибкой
curl --max-time 20 --socks5-hostname <хост>:1080 https://api.ipify.org
```

Это важно, потому что последствия серьёзные. Опубликованный на wildcard-адресе,
это открытый SOCKS5-прокси. Порт 1080 сканируют непрерывно, открытые прокси
находят за часы, они попадают в публичные списки прокси, а оттуда — в репутационные
блок-листы: быть открытым прокси уже достаточная причина для внесения. После этого
по вашему каналу, внутри вашего туннеля, идёт чужой трафик, и фильтрация исходящих
портов его не видит.

## Управление

```
vps-psiphon status                  IP выхода, страна, капча, скорость
vps-psiphon verify                  проверка доступности извне и работы SOCKS
vps-psiphon routing                 правила для панели с объяснением
vps-psiphon rotate                  новый туннель, новый выход, следующий шаг пула
vps-psiphon region DE | auto        закрепить одну страну
vps-psiphon pool 'DE NL FR'         задать пул ротации
vps-psiphon accept 'DE NL' | any    какие вердикты Google допустимы
vps-psiphon update-image [--check]  перейти на свежую сборку отслеживаемого тега
vps-psiphon notify-test             тестовое сообщение в Telegram
vps-psiphon speed                   скорость через туннель
vps-psiphon logs / watchdog         лог контейнера / журнал watchdog
vps-psiphon uninstall               удалить всё, что было записано, включая саму команду
```

`rotate`, `region`, `pool`, `accept` и `update-image` используют одну блокировку с
watchdog и установщиком. Поэтому ручная команда никогда не попадёт в середину
проверки или переустановки.

## Обновление образа

Образ закреплён по digest, чтобы код на ноде не менялся незаметно. Но из-за этого
он и не получает исправлений сам. `IMAGE` хранится в виде `repo:tag@sha256:…`:
запускается digest, а тег определяет, за чем следят обновления. По умолчанию это
`:latest`. Нода, установленная с `--image repo:v2`, продолжает следить за `:v2`.

- `vps-psiphon update-image --check` скачивает отслеживаемый тег и показывает,
  сменился ли digest. Ничего не меняет.
- `vps-psiphon update-image` переключается на новый digest, перезапускает туннель
  (активные соединения обрываются) и удаляет старый образ.
- `vps-psiphon update-image repo:v3` переключается **и делает `:v3`
  отслеживаемым тегом** на будущее. Голый digest (`repo@sha256:…`) закрепляет эту
  сборку и сохраняет текущий тег.

Переустановка сохраняет и digest, и отслеживаемый тег. `--image repo@sha256:…`
без тега при переустановке тоже сохраняет прежний отслеживаемый тег.

## Уведомления и метрики

Оба выключены, пока их не настроят.

- **Telegram**: `--tg-token <токен бота> --tg-chat <id чата>`. Watchdog присылает
  сообщение:
  - при каждой ротации — с причиной, старым и новым выходом и шагом пула;
  - при первом появлении выхода в запрещённой стране;
  - если после ротации туннель не поднялся.

  Сообщения отправляются напрямую, не через туннель. Токен хранится в
  `/etc/default/vps-psiphon` с правами 0600 и никогда не передаётся в командной
  строке. Проверить настройку: `vps-psiphon notify-test`.
- **Prometheus**: если есть каталог `/var/lib/node_exporter/textfile_collector`
  (или `--metrics-dir` указывает на другой), watchdog после каждой проверки пишет
  туда `vps-psiphon.prom`: `vps_psiphon_up`, `vps_psiphon_check_ok`,
  `vps_psiphon_throughput_kbps`, `vps_psiphon_window_failures`,
  `vps_psiphon_rotations_total`, `vps_psiphon_last_rotate_timestamp_seconds`,
  `vps_psiphon_captcha`, `vps_psiphon_country_info{gl="XX"}`,
  `vps_psiphon_last_check_timestamp_seconds`.

Лог watchdog ротируется раз в неделю через `/etc/logrotate.d/vps-psiphon`.

## Что изменено в этой копии

| | |
|---|---|
| **Образ по умолчанию закреплён по digest** | в оригинале — `:latest`, который заново разрешается при каждом pull: код на ноде может смениться без единой локальной правки и без предупреждения. `--image` по-прежнему принимает плавающий тег, но с предупреждением. |
| **Ограничения контейнера** | `--memory 512m`, `--pids-limit 256`, ограничение размера логов. На ноде с 1 ГБ OOM killer выбирает самый большой процесс, а это xray, не psiphon. Меняются через `--memory` / `--pids-limit`. |
| **`routing`** | печатает правила для панели, без которых outbound бесполезен, включая обработку UDP. |
| **`verify`** | отвечает на вопрос «доступен ли прокси извне» так, как проверки TCP-соединением не могут. |
| **Проверка ввода** | каждый флаг проверяется до записи чего-либо; коды стран нормализуются. |
| **Переустановка сохраняет состояние** | регион, образ, настройки и уведомления переживают повторный запуск, а не сбрасываются молча. |
| **Исправления watchdog** | загрузка, оборвавшаяся по таймауту, считается медленной, а не мёртвым туннелем; `status` применяет deny-список так же, как watchdog; одна блокировка для watchdog, ручных команд и установщика. |
| **`update-image`, уведомления, метрики** | открытое обновление закреплённого digest с отслеживанием тега; уведомления в Telegram; метрики для node_exporter; ротация лога. |
| **Тесты и CI** | `bats tests` и `tests/lint.sh` (shellcheck, включая генерируемые скрипты) запускаются при каждом push. |

Сам watchdog качества выхода — главная причина выбрать это семейство скриптов —
придуман в оригинальном проекте. Изменения выше исправляют и дополняют его, не
меняя того, что он оценивает.

## Выбор страны выхода

Psiphon держит выходы не везде. Какие регионы реально доступны, видно по списку
серверов, который скачивает сам клиент:

```bash
strings -a /opt/vps-psiphon/config/ca.psiphon.PsiphonTunnel.tunnel-core/datastore/psiphon.boltdb \
  | grep -oE '"region":"[A-Z]{2}"' | sort | uniq -c | sort -rn
```

На момент написания это 26 стран: `CA US DE GB NL FR SE IT PL IN JP SG RS AU AT
BE IE ES CH DK CZ NO RO LT ID BR`. Если запросить страну не из списка, watchdog
будет бесконечно делать ротации и ни разу не попадёт. Заметно отсутствуют Кавказ
и Центральная Азия: Армения, Грузия и Казахстан так недоступны.

## Предупреждения

**Не ставьте это на сервер внутри страны, из которой обходите блокировки.**
Клиент Psiphon генерирует узнаваемый трафик обхода блокировок. Под DPI его можно
и заблокировать, и использовать, чтобы опознать сервер, на котором он работает.
Место для него — зарубежная нода, до которой вы уже добираетесь другим
транспортом.

**Запустить образ вручную — не то же самое, и разница называется «открытый
прокси».** Внутри контейнера psiphon слушает `0.0.0.0`, поэтому обычный
`docker run -p 1080:1080` открывает SOCKS5 — а вместе с ним и HTTP-прокси — на
всех адресах хоста, без авторизации. Этот установщик никогда не публикует на
wildcard-адресе. `--bind`, который вы указали сами, применяется как есть, и
защищать этот адрес тогда — ваша задача.
